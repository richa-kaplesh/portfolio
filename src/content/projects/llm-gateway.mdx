## Problem

Free LLM tiers are small and strict. Groq allows a few thousand tokens per minute plus a daily cap per key. OpenRouter allows 50 requests a day per account. An app that calls one provider directly runs out within minutes, then fails slowly.

The first version of this gateway did exactly that. It treated providers as the unit of capacity, retried in place with sleeps, and spent up to 26 seconds before failing.

## Core idea

The thing that really has a quota is **one API key × one model**, not a provider. The gateway calls each one a _deployment_ and declares it in a YAML file:

```yaml
- id: groq-1
  provider: groq
  adapter: openai_compatible
  key_env: GROQ_API_KEY_1
  model: openai/gpt-oss-20b
  limits: { rpm: 30, tpm: 8000, rpd: 1000, tpd: 200000 }
  tier: smart
```

The live pool is 8 deployments: 3 Groq keys × 2 models, plus 2 OpenRouter keys. The registry refuses to boot on a bad entry, because a silently skipped key is silently lost capacity.

Counting this way changes what a failure means. A 429 belongs to one account, so only that key cools down. A timeout or a 5xx means the model itself is broken, so a circuit breaker opens for provider × model and every key of that model is skipped.

**Two random choices, not the single best.** Always picking the top score sends every request to whichever key's lagging score looks best. Drawing two and taking the better one avoids the herd.

**Fail over, don't retry in place.** There are at most 2 extra attempts after hard failures. 429s and local refusals don't use up that budget.

**Daily quotas are first-class.** The last 10% of each key is reserved for conversations already mid tool-loop, so work that has spent calls can finish.

## Results

The largest change was in the tail. Three 2-second sleeps on the same key plus a 20-second queue gave a p95 of 25.7 s. Failing over at once brought it to 0.99 s, while p50 moved from 0.61 s to 0.52 s. Attempts spread across the three Groq keys as 61 / 58 / 58.

The before and after windows are different traffic, so read them as the system in use, not as a controlled experiment. Capacity was measured separately and locally, against a mock provider: two instances sharing Redis handled about 3,000 calls per minute at 100 users, with a p95 of about 2.3 s.

## What I'd do next

Load testing found problems that are not fixed yet:

- About 37 Redis commands per call, mostly sequential. They cost about 22% of throughput at 50 users.
- Two random choices can starve a key for good, because its latency score only updates when it serves a call.
- Throughput falls past the knee instead of levelling off.
- Admission limits are per instance, not global.

The [README](https://github.com/richa-kaplesh/LLM-Gateway#readme) has every design decision, the error taxonomy and the engineering log. [QueryMind](/projects/querymind) is a real client of this gateway.
